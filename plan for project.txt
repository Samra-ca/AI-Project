# **Complete Hackathon Project Plan — Mind to Machine Hackathon**

I've carefully reviewed all **4 pages** of your uploaded *Mind to Machine Hackathon – Student Brief (18 November 2026)*.

My recommendation is to build a **Smart AI-Powered Hackathon Planning Agent** with a professional web dashboard, an AI-powered message understanding system, automatic constraint validation, budget calculations, and an explainable decision trace.

We will use **PostgreSQL as the only database** if we implement a backend. We will not use MongoDB, Firebase, SQLite, or any other database.

The most important thing: this should not be just a chatbot that reads messages. It must be an agent system that reads messages, understands changing requirements, makes decisions, rejects incorrect information, and updates the existing event plan.

## **1. Project objectives and requirements**

According to page 1 of the brief, the system must:

1. Read every message from a text file exactly as provided.
2. Process every message using the same command, without manual flags or hints.
3. Record every AI model call with its model name, area, input, output, and actual token counts.
4. Accept additional messages after the initial run and update the existing plan.
5. Detect conflicts and invalid messages, preserve valid constraints, and explain rejection reasons.
6. Provide a UI showing the plan, trace, and rejected messages.

## **6. Message processing and conflict detection**

This is one of the most important scoring areas.

The system must understand that a newer message is not automatically correct.

For example:

| Message                           | Expected decision                 | Reason                               |
| --------------------------------- | --------------------------------- | ------------------------------------ |
| Standard lunch Rs. 1,000          | Superseded                        | Newer price provided                 |
| Standard lunch Rs. 1,200          | Accept                            | Updated price                        |
| Basic lunch Rs. 800               | Accept as alternative             | Valid package                        |
| DJ for Rs. 50,000                 | Do not automatically approve      | Request, not an approved requirement |
| Judge arriving 10 minutes late    | Accept with scheduling adjustment | Operational update                   |
| Caterer reducing 177 boxes to 100 | Reject                            | Insufficient food quantity           |

### **Conflict detection rules**

Implement the following checks:

1. **Authority:** Who issued the message? Is that person authorized to change the requirement?
2. **Recency:** Is the information newer than an existing fact?
3. **Explicit approval:** Is this a confirmed decision or merely a suggestion?
4. **Feasibility:** Does the new information satisfy existing constraints?
5. **Capacity:** Does the venue accommodate everyone?
6. **Budget:** Does the updated expenditure remain within Rs. 650,000?
7. **Completeness:** Does the plan still cover all five required areas?
8. **Consistency:** Does the new message contradict another accepted fact?

For unseen messages, the system must not rely on specific sender names or hardcoded sample phrases. It should extract the intent and compare it against the existing constraints.

A crucial distinction: an authorized correction can supersede an older fact, but an ordinary suggestion cannot silently override an approved requirement.

## **8. AI model calls and trace management**

This is a major scoring requirement.

The brief gives six possible area tags:

- reading
- venue
- schedule
- food
- judging
- budget

Every model call must have exactly one appropriate area tag.

Example trace structure:

| Call | Model     | Area    | Purpose                       |
| ---- | --------- | ------- | ----------------------------- |
| 1    | Small LLM | reading | Extract message facts         |
| 2    | Small LLM | venue   | Understand venue constraints  |
| 3    | Small LLM | food    | Understand updated food offer |
| 4    | Small LLM | judging | Interpret judge requirements  |

These are illustrative calls, not actual measured token results. The implementation must record the real calls and their actual provider-reported token usage.

### **Trace data structure**

Every trace record should contain:

```
{
  "call_number": 1,
  "model_name": "actual-model-name",
  "area": "reading",
  "input": "Actual model input",
  "output": "Actual model output",
  "input_tokens": 0,
  "output_tokens": 0,
  "total_tokens": 0,
  "duration_ms": 0
}
```

At the end:

```
========== EXECUTION SUMMARY ==========

Total model calls: Actual count
Reading calls: Actual count
Venue calls: Actual count
Schedule calls: Actual count
Food calls: Actual count
Judging calls: Actual count
Budget calls: Actual count

Total input tokens: Actual count
Total output tokens: Actual count
Total tokens: Actual count
=======================================
```

Never invent token counts or report estimates as actual usage.

### **Token optimization strategy**

- Use one message-reading call where possible.
- Extract structured facts in a compact format.
- Use Python for arithmetic.
- Use Python for capacity checks.
- Use Python for budget calculations.
- Avoid calling the model for information already extracted.
- Use targeted calls only for affected planning areas.
- Cache previously extracted facts.

The organizers award five points for token efficiency and an additional ten-point bonus for using only models from their small-model list, including eligible local models. The exact approved list must be confirmed with the organizers.&#x20;

## **9. One-command execution system**

This requirement must be implemented carefully.

The judges will provide an unseen message pack. Your team must run it using one command without manually selecting agents or providing flags.

I recommend:

```
python run.py
```

The command should automatically:

1. Read the configured message file.
2. Preserve all original messages.
3. Identify new messages.
4. Extract facts.
5. Identify conflicts.
6. Generate or update the plan.
7. Validate all five areas.
8. Save the plan in PostgreSQL.
9. Generate the complete execution trace.
10. Export the final plan and trace.

The same command should work for both initial execution and subsequent updates.

### **Incremental update mechanism**

Suppose Finance sends:

> The printing bill came in at Rs. 15,000, not Rs. 10,000.

The system should:

- Identify the updated printing cost.
- Check the source and whether it is an authorized correction.
- Update the budget.
- Recalculate total expenses and remaining balance.
- Preserve the previous plan version.
- Save the new plan.
- Record the decision in the trace.

New total:

\\[ 524,000+5,000=529,000 \\]

Remaining budget:

\\[ 650,000-529,000=121,000 \\]

Only the budget area should need a model call if the correction is already unambiguously understood and the system can handle the rest through Python.

For a more complicated message, the system can call the reading agent and then only the affected planning modules.

**Update limits:**

- Maximum five model calls.
- Maximum one minute.
- Do not regenerate unaffected areas.
- Revalidate the entire plan using Python rules after an update.

The complete run must finish within two minutes.&#x20;
